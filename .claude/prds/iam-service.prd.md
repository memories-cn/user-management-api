# 基于 ZITADEL 的多租户用户管理与授权服务（IAM Service）

## Problem

SaaS 产品以 ZITADEL 作为身份认证基础设施，但 ZITADEL 只回答"你是谁"，不承载业务层的租户成员关系、租户内角色与资源级权限。业务侧缺少唯一的授权事实来源，各业务服务各自实现一套授权逻辑，导致权限口径不一致、跨租户越权风险无法系统性拒绝，高风险权限变更也没有统一入口与审计留痕。

不解决的代价：越权问题只能靠各业务服务自觉防守，一次建模错误就是一次跨租户数据泄露；权限调整需要逐个服务改代码；合规与安全事件无法回答"谁在哪个租户、什么时候、改了什么权限"。

## Evidence

- **Assumption — needs validation via 对现有业务服务授权实现现状的盘点 + 平台管理员/租户管理员访谈。** 目前没有用户原话、工单、线上指标或已观察到的越权事件作为直接证据。
- 文档依据（非用户证据）：`docs/TDD.md` v1.0-draft 已明确"ZITADEL 是身份事实来源，本服务是业务授权事实来源"的职责边界，并列出 8 项建设目标与 6 个交付阶段。这是设计结论，不能替代问题验证。
- **TBD — 越权事件频率、当前各服务重复实现的授权代码规模、管理员完成一次成员权限调整所需时长。** 需要在 MVP 前通过现状盘点补齐，用于把下面 Success Metrics 中的目标值从工程目标升级为可承诺指标。

## Users

- **Primary：租户管理员（owner / admin）** — 在管理后台管理本租户的成员、角色与权限。触发点：新成员加入、成员职责变更、离职成员权限回收、需要查看本租户操作留痕。
- **Primary：平台管理员** — 管理租户生命周期与处理安全/合规事件。触发点：开通或停用租户、处置越权事件、审计高风险操作。
- **Secondary：业务微服务（服务身份调用方）** — 在处理业务请求前，询问"该用户在本租户能否对该资源执行该操作"，而不是自行维护一套权限副本。
- **Not for**：
  - 终端登录用户——登录、注册、密码找回、MFA 由 ZITADEL 承担，本服务不提供。
  - 想用本服务替代 ZITADEL Console 管理 ZITADEL 实例的人。
  - 需要 ABAC / ReBAC / 组织树继承 / 策略脚本引擎 / 审批流的团队（首期不支持）。
  - 想把业务领域数据迁入 IAM 数据库的团队（违反职责边界）。

## Hypothesis

We believe **提供以租户为作用域的成员关系、租户内角色权限配置，以及统一的授权判定能力** will **让业务服务不再各自实现授权逻辑，并使跨租户越权被系统性地默认拒绝** for **租户管理员、平台管理员与业务微服务调用方**。

We'll know we're right when **跨租户越权安全回归用例 100% 通过（Tenant A 的用户无法读取 Tenant B 的成员；篡改请求中的租户标识不提升权限；跨租户角色分配被拒绝），且至少 1 个业务服务在生产链路改用统一授权判定后不再保留自有权限副本**。

## Success Metrics

| Metric | Target | How measured |
| --- | --- | --- |
| 跨租户越权回归用例通过率 | 100% | 安全回归测试套件（越权 / 跨租户 / 撤权），作为 CI 门禁 |
| 未定义权限的默认决策 | 100% deny | 授权判定测试：无角色、无策略的请求必须返回拒绝而非放行 |
| 租户级接口的租户隔离覆盖 | 100% | 每个租户级接口都有"非本租户成员访问被拒"的用例 |
| 授权依赖不可用时的行为 | 0 次自动放行 | 故障注入测试：数据库 / 缓存 / 授权引擎不可用时必须失败关闭 |
| 高风险操作审计覆盖率 | 100% | 成员移除、角色分配、角色权限变更、租户停用、平台管理操作的审计记录对账 |
| 本地授权判定延迟 P95 | ≤ 10 ms | 目标部署环境压测（TDD 初始工程目标，**尚未实测**，需压测验证） |
| 常规业务 API 延迟 P95 | ≤ 200 ms（不含交互式登录） | 同上，需压测验证 |
| 撤权时效 | 成员移除 / 用户禁用后，既有缓存授权在约定窗口内失效 | 撤权测试 + 缓存失效验证；窗口时长待确认（见 Open Questions） |

## Scope

**MVP** — 对应 TDD Phase 1–5，目标是让"身份接入 + 租户成员 + 租户内 RBAC + 管理后台 API + 审计"这条主链路可用并被测试证明：

1. **可运行的服务骨架**：服务能在本地与容器环境启动，存活/就绪检查可用，测试可重复执行。
2. **ZITADEL 身份接入**：验证访问令牌并构造可信身份对象；本地业务用户按需同步；无效、过期、受众错误的凭证被拒绝；身份平台不可用时不得建立可信身份。
3. **租户与成员**：租户创建与查询、成员邀请/停用/移除、当前用户的租户列表；所有租户级接口强制执行"用户有效 + 租户有效 + 成员关系有效 + 资源属于该租户 + 权限通过"的完整校验链。
4. **租户内 RBAC**：租户内角色与系统权限目录、成员角色分配、统一的授权判定接口；角色与权限变更具备事务一致性，变更后可正确撤权。
5. **管理后台 API 与审计**：权限目录查询、角色权限配置、管理接口的分页与过滤、统一错误码与 API 文档、高风险操作审计留痕。

**Out of scope**

- 自建登录、注册、密码校验、密码找回、MFA —— 由 ZITADEL 承担，本服务不重复实现。
- 自建 OAuth 2.0 / OIDC Identity Provider —— 本服务仅作为资源服务器。
- ABAC、ReBAC、组织树继承与策略脚本引擎 —— 复杂度高且无需求证据，延后评估。
- 工作流、审批流、企业 HR 组织管理 —— 无证据支撑。
- Vue 管理后台的前端实现 —— 本 PRD 只约束其所需的管理 API；前端是否纳入本次交付见 Open Questions。
- 将各业务服务的领域数据迁入 IAM 数据库 —— 违反"身份与业务授权分离"的边界。
- 平台管理员的完整运营控制台 —— MVP 仅提供独立的平台授权路径与强制审计，不做完整运营界面。
- 多区域部署、数据 residency —— 首期不涉及。

## Open Questions

- [ ] **访问令牌的验证方式**：本地验签还是令牌自省？取决于实际客户端拿到的令牌类型，直接决定认证链路与配置校验。
- [ ] **平台管理员的边界与授予方式**：平台权限如何定义与授予、是否与租户角色完全独立、由谁授予？
- [ ] **租户创建权限**：开放自助创建，还是仅平台管理员或受控流程可创建？
- [ ] **成员邀请机制**：受邀人身份如何识别（不得仅凭邮箱字符串创建可登录的本地用户）、邀请有效期、重复邀请与接受流程？
- [ ] **撤权时效**：用户禁用、删除、成员移除后，既有会话与缓存授权必须在多久内失效？
- [ ] **多实例策略一致性的可接受窗口**：策略更新在各实例间允许的最大延迟是多久？
- [ ] **业务服务接入形态**：统一授权走远程 API 还是共享 SDK？MVP 选择哪一个。
- [ ] **Vue 管理后台前端是否在本次交付范围内？**
- [ ] **平台管理员与租户管理员的权限是否需要支持租户数据的只读运营视图？**

## Risks

| Risk | Likelihood | Impact | Mitigation |
| --- | --- | --- | --- |
| ZITADEL Organization 与业务 Tenant 概念混淆导致建模错误 | 中 | 高 | 首期明确分离，业务租户不强制映射到 Organization |
| 令牌类型与验证方式不匹配，认证链路返工 | 中 | 高 | 先确定实际客户端令牌类型再定验证方式；认证能力对上层接口抽象，避免扩散 |
| 授权策略与业务关系表事务不一致，产生半成品权限数据 | 中 | 高 | 用真实数据库的集成测试验证原子性；无法纳入同一事务的副作用采用显式补偿机制 |
| 多实例策略更新延迟导致撤权滞后 | 中 | 中 | 明确可接受的撤权窗口；引入策略版本号与失效传播机制 |
| 平台管理员越权 | 低 | 高 | 平台权限走独立的显式授权路径，禁止用通配租户或空租户隐式提权；全部操作强制审计 |
| 用户状态同步延迟（禁用/删除后仍可访问） | 中 | 高 | 明确撤权时效并写入验收测试；高风险操作不依赖长期缓存 |
| 业务服务绕过 IAM 自行授权 | 中 | 高 | 提供统一授权入口降低接入成本；业务端保留强制校验 |
| 权限目录被租户随意扩展 | 低 | 中 | 可执行权限集合由系统维护，租户只能在既有集合内组合自定义角色 |
| 性能与并发指标被误读为已达成承诺 | 中 | 中 | 在文档与报表中统一标注为"待压测验证的工程目标" |
| 移除最后一个有效 Owner，导致租户无人可管 | 中 | 高 | 系统级保护：禁止移除最后一个有效 Owner，并纳入回归测试 |
